# HANDOVER.md — pdfjig

Claude Code への引き継ぎ文書。
前提知識は `SPEC.md`、遵守事項は `CLAUDE.md` にある。**両方を読んでから着手すること。**

現状: Phase 0 〜 Phase 4 まで完了。`pdf-core` は基盤型・テキスト抽出・ページ操作・描画、
`pdf-desktop` はサムネイル一覧、ドラッグ&ドロップ並べ替え、削除・回転・範囲指定、
結合・分割、パスワード入力までが動き、jpackage で MSI / EXE / ZIP を作れる。

**残っているのは v0.1.0 のタグ打ちと、その前の実機確認だけである**（下の「Phase 4 の残り」）。
その先は M1。着手前に、未決事項のうち設定ファイルの配置・ログ方針・権限フラグへの態度を決める必要がある。

## 確定している判断

議論を経て決定済み。再検討は不要。

| 項目 | 決定 | 理由 |
|---|---|---|
| スタック | Java 21 + JavaFX + PDFBox 3 | 表抽出の成熟実装が Java にしかない |
| ライセンス | Apache-2.0 | iText (AGPL) を排除する制約でもある |
| Excel 出力 | M1 に含める | CSV は先頭ゼロ消失・日付自動変換で実務データを壊す |
| M0 の UI | サムネイル並べ替えまで実装 | リスト表示だけなら既存 CLI に対する優位性がない |
| Maven Central | 初版では使わない | アプリケーションでありライブラリではない |
| 配布 | GitHub Releases + jpackage | MSI / EXE |
| 表示名 | `PDFjig` | コマンド名・パッケージ名は `pdfjig` のまま。コマンドは小文字が自然 |
| ベンダー名 | `PROPAGANDIST CORPORATION` | MSI の発行元 |
| 配布形式 | MSI + EXE + ZIP | 形式ごとに役割を分ける（下記 4-1） |
| 最小 Windows | 10 21H2 (x64) | サポート終了済みの古いビルドを切る |
| JavaFX ランタイム | Gluon の jmods を Gradle で取得 | JavaFX 同梱 JDK を全員に強いない |
| MSI UpgradeCode | `3210BCE4-3635-4EFC-8EC1-DC77881091BB` | **二度と変えない。** 変えると旧版が残る |

## Phase 2: pdf-core（M0 範囲）

依存のないところから積む。

### 2-1. 基盤型

`PdfDocument`（AutoCloseable）、`PdfjigException`、`ErrorCode`、`PageRange`、`Rotation`。

`PdfDocument.open(Path, char[])` の時点で INV-5 が関わる。
パスワードはコンストラクタで使用後に即ゼロ埋めし、フィールドに保持しない。

### 2-2. TextExtraction

`extractAll` / `extractByPage` / `extractWithPositions`。
PDFBox の `PDFTextStripper` を使う。座標付き抽出は `PDFTextStripper` を継承して
`writeString(String, List<TextPosition>)` をオーバーライドする。

### 2-3. PageOperations

`merge` / `split` / `reorder` / `rotate` / `extractPages` / `deletePages`。

**ここで暗号化の伝播を必ず実装する**（`SPEC.md` §4.3）。
M0 では暗号化「設定」機能はないが、暗号化された入力を受け取る可能性はある。
`EncryptionPropagation` の判定と警告発出は M0 の時点で入れておく。
後から足すと、既に平文出力してしまった利用者が発生する。

### 2-4. テスト

各操作について、ページ数・ページ順・回転角が期待通りかを検証する。
フィクスチャ PDF は PDFBox で生成するユーティリティをテストコードに置き、リポジトリには
生成済みファイルを最小限だけ置く。

## Phase 3: pdf-desktop（M0 範囲）

### 3-1. サムネイル一覧

要求: 固定サイズ、遅延レンダリング、LRU キャッシュ。

実装上の要点:

- `PDFRenderer#renderImageWithDPI` は必ず `Task` の中で呼ぶ（`CLAUDE.md` JavaFX 節）
- 可視範囲外のページはレンダリングしない。`ListView` / `GridView` の cell factory で
  cell が表示された時点でレンダリングを開始する
- キャッシュサイズは上限ページ数で管理する（例: 直近 200 ページ）。
  メモリ量ではなく枚数で切るほうが挙動が読みやすい
- レンダリング中はプレースホルダを表示し、UI をブロックしない

### 3-2. ドラッグ&ドロップ並べ替え

単一文書内のみ。文書間のページ移動は実装しない。

並べ替えは UI 上の順序リストを更新するだけで、この時点ではファイルを書き換えない。
「保存」操作で `PageOperations.reorder` を呼ぶ。

### 3-3. 基本操作の UI

結合（複数ファイル選択）、分割、ページ削除、回転、範囲抽出。
それぞれ確定的処理を直接呼ぶ。承認フローは不要（AI が関わらないため）。

メニューに加えて、繰り返し使うものはツールバーにも出す（Phase 4 で追加）。

### 3-4. パスワード入力ダイアログ

暗号化された PDF を開こうとした場合に表示する。
`PasswordField` を使い、`char[]` で受け渡す。入力値を `String` に変換しない。

M0 では「開く」だけ。設定・解除は M1。

## Phase 4: リリース

### 4-1. jpackage（実装済み）

`installDist` → `jlink` → `jpackage` の 3 段。`./gradlew :pdf-desktop:packageAll -Pversion=0.1.0`
で `dist/` に 3 つの成果物ができる。手元で回すには WiX 3.14 を PATH に通す必要がある
（jpackage が要求するのは 3.x で、v4 では動かない）。

配布形式は役割で分けた。同じものを 2 つ並べるのではなく、

- **EXE** — ユーザー単位。管理者権限が要らない。個人向け
- **MSI** — マシン単位。`--win-dir-chooser` で入れ先を選べる。情報システム部門による一括配布向け
- **ZIP** — インストール不要。インストーラ自体が使えない環境向け

EXE と MSI は同じ製品であり、両方を同時には入れられない。jpackage は ProductCode を
名前とバージョンから決めており、両者で同一になるため。二重に入るよりは入らないほうが説明できる。

実測サイズは各 60MB 前後（ランタイムイメージ 59MB、アプリイメージ 82MB）。
→ **2026-08-22 訂正: POI を外して各 45MB 前後になった**（MSI 45.2 / EXE 45.8 / ZIP 44.1 MB。
アプリイメージ 63MB。ランタイムイメージは 59MB で変わらない——外した 2 モジュールは小さい）。
M1 で POI を戻せば元の水準へ戻る。

### 4-2. GitHub Actions によるリリース自動化（実装済み）

`.github/workflows/release.yml`。タグ `v*` の push、または `workflow_dispatch` で走る。
`runs-on` は `windows-2022` に固定し、WiX もランナーイメージのプリインストールに頼らず
ワークフロー内で用意する。イメージ更新で黙って壊れるのを避けるため。

**draft リリースとして作る。** 実機で触ってから公開する。

### 4-3. Phase 4 の残り

ここから先は人が行う。

1. **実機確認**（下の「リリース前の確認」）
2. `docs/RELEASE_NOTES.md` の内容を確認する（リリース本文になる）
3. `git tag v0.1.0 && git push origin v0.1.0`
4. Actions が draft リリースを作るので、成果物を触ってから公開する

**この時点で AI 機能はゼロ。それで問題ない。**
AI なしで実用に耐えるツールとして一度リリースした事実を履歴に残すことが、
`CLAUDE.md` INV-3 の裏付けになる。

### 4-4. リリース前の確認

**「CI は GUI を起動できない」という前提は 2026-08-22 に無くなった**
（下の「UI テストの自動化」）。いま自動で見ている範囲と、人が見る範囲を分けてある。

**この 2 つを混ぜないこと。** CI が緑であることを実態より広く読むと、
確認したつもりの穴がそのまま配られる。

#### CI が見るもの

| いつ | 何を |
|---|---|
| `build`（push / PR、windows のみ） | 開く・回す・消す・並べ替える・区切って分割する・保存する。パスワード付きの文書を開く（`:pdf-desktop:uiTest`） |
| `release`（タグ） | ZIP を展開して `PDFjig.exe` が起動し、ツールバーが組み上がるところまで |

#### 人が見るもの

1. **ZIP を展開し `PDFjig.exe` を直接起動** → 管理者権限なしで起動する
   ── CI も見ているが、実機でも一度は触ること。ランナーは検証用の綺麗な Windows であり、
   利用者の環境ではない
2. **EXE を実行** → 管理者昇格を求められずに入る。スタートメニューに `PDFjig` が出る
   ── ランナーで入れると、消すところまで含めないと片手落ちになり、失敗したときに
   ランナーの状態が壊れる
3. **MSI を実行** → インストール先を選べる。`%ProgramFiles%` に入る（同上）
4. **アンインストールでファイルが残らない**（同上）
5. **同じ MSI をもう一度入れて上書きになる**（UpgradeCode の確認。同上）
6. **ネットワークを遮断したまま**一連の操作が動く（INV-3 の確認）
   ── ランナーで遮断すると Gradle も止まる。何が原因で落ちたのか切り分けられない
7. **日本語のファイル名・パスの PDF を開ける**
   ── ランナーのロケールは利用環境と違う。日本語環境で見るほうが確か
8. **表示倍率 150% でサムネイルが眠くない**
   ── 目で見る以外にない
9. **ドラッグでの並べ替え**
   ── **★ ここは CI で守られていない。** `ReorderUiTest` は手元では走るが、
   windows ランナーでは 1 本で 19 分かかるため CI から外してある（上の「UI テストの自動化」）。
   **動くこと自体を人が確かめる必要がある。** 掴んだ感じが自然かどうかも同じ場で見る

タグを打つ前に `v0.1.0-rc1` のような捨てタグでワークフローを一度通しておくと、
CI 側の失敗を本番のタグで踏まずに済む。確認後にタグとドラフトを消す。

## 実装中に決めた判断

仕様に書かれておらず、実装を進めるために決めた事項。いずれも方針が違えば差し戻せる。

### テキスト抽出（Phase 2-2）

- [ ] 抽出時に座標順への並べ替え（`setSortByPosition(true)`）を既定にした。
      コンテンツストリーム順のままだと多段組の文書で読み順が崩れ、`pdf-ai` に渡す
      テキストの品質に直結するため
- [ ] 改行を LF に固定した。`System.lineSeparator()` に従うと、同じ入力から
      環境ごとに異なる出力が出る
- [ ] `PositionedText` の座標系をページ左上原点とした（PDF 本来は左下原点）。
      画面表示と向きを揃えるため。tabula-java は PDF 座標系を使うので、
      M1 の表抽出では変換が要る

### ページ操作（Phase 2-3）

- [ ] 出力先に同名のファイルがある場合は必ず失敗させる（`OUTPUT_ALREADY_EXISTS`）。
      上書きするかどうかは利用者の判断であり、確認は UI / CLI の責務とする。
      入力と同じパスを出力に指定して入力を壊す事故もこれで同時に防がれる
- [ ] `rotate` の指定は現在の回転角への加算とした。UI の「右に回す」という操作と
      一致させるため。絶対角の指定にはしていない
- [ ] 分割の出力ファイル名を `<入力名>_001.pdf` とした
- [ ] `EncryptionPropagation.INHERIT` / `PROMPT` は M0 では未対応とし、指定されたら
      失敗させる。引き継ぎには元のパスワードが必要であり、パスワードを受け取る経路を
      持つ M1 の暗号化機能とあわせて実装する
- [ ] パスワードが必要な入力に対するページ操作は M0 では行えない。同じく M1 で対応する
- [ ] `SPEC.md` §4.2 にない `PageOperations.assemble(Path, List<PageSelection>, Path)` と
      値型 `PageSelection` を追加した。UI で並べ替え・削除・回転を続けて行った結果は、
      一度の保存で確定させないと「並べ替えた状態で回転したら並べ替えが消えた文書が
      出てくる」ことになる。個別操作のままでは利用者を誤解させるため
      （`CLAUDE.md` 優先順位 2）。既存の `reorder` / `rotate` / `extractPages` /
      `deletePages` はそのまま残してある。
      → **承認され、`SPEC.md` §4.2 に追記済み**（Phase 4）
- [x] 上に伴い、UI では回転も編集セッションに含めた。`HANDOVER.md` 3-3 は回転を
      独立した操作として挙げているが、サムネイル一覧の上で回して保存するほうが
      並べ替え・削除と揃う。独立操作に戻すべきなら指示がほしい

### UI（Phase 3）

- [x] サムネイル一覧は縦 1 列の `ListView` にした（→ Phase 4 でグリッドに変更）。`GridView` は ControlsFX への依存が
      必要になる。仮想化が効き、セルが表示された時点で描画を始められる点は同じ
- [x] サムネイルの長辺は 160px、キャッシュは 200 枚とした（→ Phase 4 で描画 220px / 表示 150px に変更）
- [ ] 保存は一時ファイルに書いてから置き換える。保存先ダイアログは上書きを確認するが
      `pdf-core` は既存の出力を拒む。先に消すと書き込み失敗で元のファイルが失われる
- [ ] 結合の入力は名前順に並べ、その順序を見せて承認を求める。ファイル選択ダイアログが
      返す順序は環境によって変わり、選んだ順に結合されると思い込ませてしまう
- [ ] UI の分割は編集中の並びを対象にする。`pdf-core` の `split` は元の並びを切るため
      使っていない
- [ ] 起動引数でファイルを開けるようにした。ファイルの関連付けから開く経路であり、
      UI を手で操作せずに動作を確かめる手段でもある
- [x] ~~JavaFX を必要とする部分（サムネイルの供給、ダイアログ）にはユニットテストを
      書いていない。Toolkit の初期化が要り、CI では Monocle などの追加が必要になる~~
      → **2026-08-22 に覆した**（下の「UI テストの自動化」）。Monocle は使わない。
      windows ランナーが対話セッションを持つことを使い、TestFX を headed で回している。
      画面に依存しない `PageOrder` と `LruCache` を先に固めてあったことは今も効いていて、
      画面のテストは「その判断が画面を通したときにも呼ばれるか」だけを見ればよくなっている

### ダイアログを始めるフォルダ（v0.1.0 の実機確認で追加）

- [ ] **`setInitialDirectory` を 4 つのダイアログのどれでも呼んでいなかった。**
      初期フォルダを決めるのは Windows の共通ダイアログ側になり、
      毎回たどり直すことになっていた。JavaFX（`WinCommonDialogs`）は
      `initialDirectory` が未設定なら `null` をネイティブへ素通しするだけで、
      その先はアプリの実行ファイルに紐づく MRU が使われる。前回のフォルダが出ることもあるが
      規則は保証されず、起動のしかたが変われば別の履歴になる
- [ ] **読む用と書く用の 2 つを覚えることにした**（`RecentFolders`）。開く・追加は読む用、
      保存・分割先は書く用。PDF を取ってくる場所と整理した結果を置く場所は違うことが多く、
      片方に引きずられるとそのつどたどり直すことになる。
      まだ使っていない側は、いま開いている文書の隣から始める。どちらも無ければ渡さず、
      今までどおり Windows の既定に任せる。初回にホームへ固定するより馴染みがある
- [ ] **覚えるのは `open(Path)` / `addDocument(Path)` の側に置いた。** ダイアログの側ではなく
      ここに置くことで、**起動引数から開く経路**（ファイルの関連付け）も同じ扱いになる。
      開くのに失敗しても覚える。パスワードが要る文書でも壊れた文書でも、
      次に PDF を探す場所は同じフォルダである
- [ ] **取り出すときに存在を確かめる。** USB を抜く、ネットワークの割り当てが切れる、
      利用者が片づける。無くなったフォルダを渡すとダイアログの出方が読めなくなる
- [ ] `RecentFolders` は JavaFX の型を持たないので**ユニットテストを書いてある**。
      上の「JavaFX を必要とする部分はテストしない」は、Toolkit の初期化が要る部分に限った話であり、
      `Path` だけを扱う判断はテストで固められる
      （その「テストしない」は 2026-08-22 に覆した。この項の判断は変わらない）

### 分割を「ここで区切る」に変えた（Phase 4）

- [ ] **UI は `EveryNPages`（N ページごとの均等割り）だけを出していた。** 均等割りが当たるのは
      「1 ページずつバラす」か「決まった枚数の綴りが連続している」場合だけで、実務の
      スキャン束は書類ごとに枚数がまちまちなのでまず当たらない。使いどころの狭い切り方だけを
      出していたことが「用途が分からない」につながった
- [ ] サムネイルを見て切れ目に印を付け、その区切りで分ける形にした。`pdf-core` の
      `AtBoundaries` と同じ考え方であり、**M2 の文書境界検出（AI）はこの仕組みに提案を
      流すだけになる**（承認 → 区切りを付ける → 分割）
- [ ] **区切りはページに紐づける**（`PageEntry`）。位置に持たせると、ページを動かしたときに
      「A と B の間で切る」が「A と C の間」に化ける
- [ ] 先頭には区切りを付けられない。先頭は区切らなくてもファイルの始まりである。
      区切りのあるページが先頭へ動いてきた場合も、その区切りは効かないものとして扱う
- [ ] `modified()` は区切りを見ない。書き出す内容が変わらないのに「未保存の変更があります」と
      出るのは筋が違う。`reset()` は区切りも外すため、メニューの文言を
      「並びと向きを元に戻す」→「編集を元に戻す」に変えた
- [ ] 区切りが 1 つも無いときの分割は何もしない。全ページを 1 ファイルに書き出しても
      分割にならず、黙ってそうするより区切りが要ることを伝えるほうが正直である
- [ ] 枚数で機械的に区切る操作は「N ページごとに区切る…」として分けた。区切りを入れる操作と
      書き出す操作を一緒にすると、どこで切られるのか確かめないまま書き出すことになる
- [ ] `PageOperations.split` / `SplitStrategy` は引き続き UI からは使わない。
      `SPEC.md` §4.2 の API であり、M2 の CLI と AI 境界検出で使う
- [ ] 区切りの縦線はタイルに重ねて描く。枠線として持たせると内側の余白が変わり、
      区切りのあるページだけ中身がずれる

### 1 ページずつの分割を独立させた（2026-08-22）

- [ ] **「全部バラす」に辿り着くのに 5 手かかっていた。** 「N ページごとに区切る…」で 1 を入れ、
      画面に戻って「分割」を押す。しかも「全部バラす」という意図から「N ページごとに区切る」を
      選び、N=1 がそれに当たると気づく必要がある。分割のうち最も頻度が高く、最も判断の要らない
      操作にしては、手数も発見性も見合っていなかった
- [ ] **上の「区切りを入れる操作と書き出す操作を分ける」判断は、切り方に判断の余地がある場合の
      ものである。** N=3 で区切ったとき、それが正しい切れ目かは中身を見ないと分からないので、
      画面で確かめる価値がある。1 ページずつには切れ目の判断が存在せず、ページ数がそのまま
      ファイル数になる。確かめるべきものが無い。**例外を作ったのではなく、元の判断の射程が
      N≥2 に限られていた**
- [ ] 「1 ページずつに分割…」を独立した操作にした（ツールバー「1 枚ずつ」）。押す → 保存先 →
      書き出しの 1 手。分割ダイアログに切り方を並べて 1 つにまとめる案は採っていない。
      全分割で 2 手増え、既存の区切り分割でも 1 手増える
- [ ] **区切りは見ないし、消しもしない。** `applyEveryNPages(1)` を内部で呼ぶ実装にはしていない。
      付けてある区切りを黙って壊すためである。「1 ページずつに」という文言が、区切りを
      見ないことを既に宣言している
- [ ] 1 ページの文書では操作そのものを無効にする。できるのは元と同じ 1 ファイルだけで分割に
      ならず、区切りが無いときと違って利用者に打つ手も無い。断るより初めから押させない
- [ ] 確認は挟まない。入力は変わらず、出力先に同名があれば 1 つも書かずに失敗する。
      枚数は状態表示が常に出しているので、何個できるかは押す前に読める
- [ ] **`PageCountPrompt` のボタンは「分割」と書いてあるのに分割していなかった**（区切りを
      入れるだけ）。「区切る」に直し、題も「N ページごとに区切る」にした。押した人が
      書き出されたと思い込む文言だった（`CLAUDE.md` 優先順位 2）
- [ ] `PageOperations.split` / `SplitStrategy` は今回も使っていない。UI が切るのは編集中の
      並びであり、上の判断は変わらない。M2 の CLI で使う

### 直した不具合（Phase 4）

- [ ] `PageOrder.pages()` が呼び出しごとに `unmodifiableObservableList` を作っていた。
      このラッパーは元の一覧を弱参照で監視するため、参照を保持しない限り GC で回収され、
      変更リスナが黙って呼ばれなくなる。**画面は開いた直後だけ正しく、しばらくすると
      更新が止まる**という追いにくい壊れ方をする。
      旧 UI では `ListView.setItems` がラッパーを保持していて表に出なかったが、
      同じ書き方をしていた状態表示（`N / M ページ`）の更新は既に壊れていた。
      ビューは 1 つだけ作って使い回す。毎回同じインスタンスを返すことをテストで固定した
- [ ] **見えているサムネイルをクリックしただけで一覧が飛んでいた**（v0.1.0 の実機確認で発覚）。
      選択が動くたびに `ListView#scrollTo` を呼んでいたのが原因。
      **このメソッドは名前に反して「見えるようにする」ではなく、その行を viewport の最上段へ送る。**
      実体は `ScrollToEvent.scrollToTopIndex()` を投げるだけで、受けた `VirtualContainerBase` が
      `VirtualFlow#scrollToTop(int)` を呼ぶ。見えている行に対して呼んでも容赦なく飛ぶ。
      同じクラスの `VirtualFlow#scrollTo(int)` のほうが目的に合い、行が見えていれば何もせず、
      はみ出していれば足りない分だけ動かす。`.virtual-flow` を引いてそちらを呼ぶことで、
      可視判定を自前で持たずに済んだ
- [ ] **上に伴い、スクロールは「選択が画面の外へ出る操作」だけの責務にした。**
      クリックとドラッグの開始は利用者がタイルの位置を見て決めた操作であり、そこで一覧を動かさない。
      矢印キー・ドロップ後・文書を開いた直後・ページが減って選択が末尾へ寄ったときだけ追いかける。
      `select` はスクロールせず、`selectAndReveal` が追いかける側という分け方にしてある
- [ ] **選択中のページがある状態で別のサムネイルを掴むと、掴んだのと違うページが動いていた**
      （同じく実機確認で発覚）。原因は、選択が動くたびに呼んでいた `ListView#refresh()` である。
      **あれは全セルを作り直す。** `Properties.RECREATE` を立てると `ListViewSkin` が
      `requestLayout` し、`VirtualFlow#layoutChildren` の `needsRecreateCells` の枝が
      `sheet.getChildren().clear()` と全セルの `updateIndex(-1)`、`cells.clear()` /
      `pile.clear()` を行う。`updateIndex(-1)` は `RowCell.updateItem(null, true)` を通って
      `ThumbnailTile.clear()` に届き、タイルの位置を `-1` に落とす。
      ドラッグは MOUSE_PRESSED → DRAG_DETECTED → DRAG_DROPPED と続く一連のジェスチャで、
      **その間にレイアウトパスが挟まる。** 掴んだ時点のタイルが別のページを受け持った後に
      `startDrag` がフィールドを読むため、掴んだのと違うページが dragboard に入っていた。
      `startDrag` 自身が冒頭で `grid.select` を呼んでおり、掴んだ瞬間に掴んだ相手を
      作り直す予約もしていた
- [ ] **選択の反映を `refresh()` からタイル自身に移した。** 選択が動いて更新が要るのは
      旧選択と新選択の 2 枚だけであり、全セルを作り直す理由がない。`ThumbnailTile` が
      `selectedIndexProperty` を見て自分で枠を当てる。`show` からは「選択中か」の引数を落とし、
      選択位置の出どころを一つにした。両方から当てられると、呼び忘れた経路で枠が残る。
      `rebuild()` の中の `refresh()`（出どころの帯が出る／消えるとき）は残してある。
      あれは内容の変わらないセルを更新するために要り、選択とは別のタイミングで走る
- [ ] **あわせて、ジェスチャの間はタイルの位置をローカルに確定させることにした。**
      `startDrag` / `completeDrag` / `select` の先頭で一度だけ読む。タイルが行セルに
      使い回される以上、ジェスチャをまたいでフィールドを読むのは危うい。上の修正で
      作り直しは起きなくなったが、**次に誰かが `refresh()` を足したときに同じ壊れ方をしない**
      ための保険であり、コストはない
- [ ] `ListView#scrollTo` と `ListView#refresh` で 2 つ続けて踏んでいる。どちらも名前から
      想像する動きより激しく、素の `ListView` の上に格子を作る以上は避けて通れない。
      同じ穴に落ちないよう、`selectedIndex` の宣言と `reveal` の Javadoc に理由を書いてある
- [ ] **ステータスバーに「AI 機能: 無効」と出していた**（同じく実機確認で発覚）。
      AI が無いことを隠さない意図（INV-3）だったが、**「無効」は「有効にできるが今は切ってある」と読める。**
      この版には AI 機能そのものが入っておらず、有効にする設定はどこにもないため、
      利用者は在りもしない設定画面を探すことになる。README とリリースノートの
      「この版に AI 機能は入っていない」という説明とも食い違っていた（優先順位 2）
- [ ] **出す先をバージョン情報のダイアログに移し、文言を「この版には含まれていません」にした。**
      ステータスバーは開いている文書の状態を出す場所であり、版の性格を混ぜると読み分けられない。
      加えて v0.1.0 では常に同じ文字列しか出ず、その行を占める意味がなかった。
      文言は `AppInfo#aiStatus` に置いてテストで固定してある（「無効」と書かないこと）。
      `AboutDialog` には `AiProvider` ではなく可否の `boolean` だけを渡す。
      この画面が要るのは可否だけで、提案の仕組みまで知る必要はない

### 使っていない POI を外した（2026-08-22）

**M1（Excel 出力）で戻す。** `SPEC.md` §85 の「Excel 出力 = Apache POI (SXSSF)」は

- **実際に使っている PDFBox（約 4 MB）の 3.5 倍**を、使っていない POI（約 14 MB）が占めていた
- **Dependabot の警告 2 件の出所がすべて POI 経由だった**（`log4j-api` 2.24.3 /
  `commons-lang3` 3.16.0）。POI を 5.5.1 へ上げても `commons-lang3` しか直らず、
  `log4j-api` は 2.24.3 のまま残るため、constraint での強制が要る状態だった
- **jlink のルートモジュール 2 つも POI のためだった**——`jdk.unsupported`
  （POI が `sun.misc.Unsafe` を使う）と `jdk.xml.dom`（xmlbeans が要求する）

`CLAUDE.md`「依存を放置しない」（分類 D の 2 項目のうち 1 つ）は、**宣言している以上
CVE を見る責任があるという意味**である。使っていないものを見続ける理由はない。

#### 戻すときにやること

1. `pdf-core/build.gradle.kts` に `implementation(libs.poi.ooxml)` を足す
   （`gradle/libs.versions.toml` の `poi-ooxml` は座標として残してある）
2. `pdf-desktop/build.gradle.kts` の `runtimeModules` に `jdk.unsupported` と
   `jdk.xml.dom` を足す。**これを忘れると jlink 後のアプリが実行時に落ちる**
3. `XSSFWorkbook` ではなく **SXSSF を使う**（`CLAUDE.md` リソース管理節）

### UI テストの自動化（2026-08-22）

**Phase 3 の「JavaFX を必要とする部分はテストしない」を覆した節である。**
覆した理由と、そのとき踏んだ罠を残す。踏み直さないために書いてある。

#### なぜ覆したか

`pdf-desktop` の画面まわりは約 3,000 行あり、動作の担保は 4-4 の手動チェックリストだけだった。
「Monocle が要るから無理」という前提を確かめ直したところ、**Monocle は要らなかった**。

#### 構成

2 つの層に分かれる。**それぞれが答える問いが違う。**

| | 何を答えるか | どこで |
|---|---|---|
| `:pdf-desktop:uiTest`（TestFX） | 画面の操作が正しい結果を出すか | `build` の windows ジョブ |
| `tools/smoke/Verify-AppImage.ps1` | 配った成果物がその環境で立ち上がるか | `release` |

- **ヘッドレスにしない。** `org.testfx:openjfx-monocle:21.0.2` は JavaFX 21 で
  `Window#_updateViewSize` を実装しておらず、表示時に `AbstractMethodError` になる
  （[TestFX/Monocle#97](https://github.com/TestFX/Monocle/issues/97)）。
  windows ランナーは対話セッションを持つのでそのまま動く。
  配布対象と同じ描画経路を通る点でも、こちらが正直である
- **`uiTest` は独立したソースセットにしてある。** `build` に含めないことを構造で担保する。
  ワークフローの `if` だけに頼ると、`build` に紛れ込んだとき黙って ubuntu でも動き出す
- **フィクスチャは `pdf-core` の testFixtures から取る**（`TestPdfs`）。
  リポジトリに PDF を置けない（INV-6）以上、生成の作法が 2 か所に分かれると必ず食い違う。
  そのため `pdf-core` に `java-test-fixtures` を入れ、`TestPdfs` をそちらへ移した

#### そのために本体へ入れた変更

**守るべき規則は `CLAUDE.md` に置いてある**（「命名」「JavaFX」「テスト」の各節）。
id の付け方、`setAccessibleText` の対象、不安定なテストをどこまで吸収してよいかは、
そちらが正である。ここに残すのは、なぜそれが要ったかだけである。

- **`FileDialogs` / `NativeFileDialogs`** — Windows の共通ダイアログは自動テストから
  操作できない。ここを差し替えられなければ「開く → 編集 → 保存」が通せない。
  UI テスト以前に、ネイティブ依存が 1 型に集まる設計改善でもある
- **`setId`** — それまで 1 度も使っていなかった。文言で節点を掴むと、画面の言い回しを
  変えるたびにテストが落ちる。`Action` レコードに id を 1 つ足し、メニューとツールバーの
  双方へ配っている。両者が同じ `Action` から作られる構造をそのまま使った
- **`setAccessibleText`** — ツールバーのボタンのみ。理由は次項

#### 踏んだ罠

**★ UI Automation から `setId` は見えない。**
JavaFX は UIA プロバイダを自前で持つ（`WinAccessible`）が、`UIA_AutomationIdPropertyId`
が返すのは `"JavaFX" + 内部連番` であり `Node#getId()` ではない（jfx21 のソース、
コメントも "Not required but useful for debugging"）。外から掴めるのは
Name（`AccessibleAttribute.TEXT`）と ControlType だけである。
**したがって起動スモークで深い操作を書くと、画面の文言を変えた瞬間に壊れる。**
「窓が出て、ツールバーが組み上がった」で止めてあるのはそのため。

**★ 窓を持つのは `Start-Process` が返すプロセスではない。**
jpackage の Windows ランチャーは自分の子として本体を起こす。実測では親は窓を持たず、
子が `PDFjig` という表題の窓を持っていた。返り値の PID だけを見ると必ず落ちる。
起動によって増えた同名プロセスを全部候補にしている。

**★ 起動スモークは Windows PowerShell 5.1 で走らせること。**
`UIAutomationClient` / `UIAutomationTypes` は .NET Framework のアセンブリであり
.NET Core には無い。`release.yml` の既定シェルは `pwsh` なので、
このステップだけ `shell: powershell` を明示している。外すと `Add-Type` で落ちる。
スクリプト自体も **UTF-8 BOM 付きで保存すること。** 5.1 は BOM 無しを ANSI として読み、
UIA へ渡す「開く」が化けてボタンが永遠に見つからなくなる。

**★ 活性でない窓への最初のクリックは消える。**
Windows は非活性の窓への 1 回目のクリックを窓の活性化に使い、その下のコントロールには
届けない。`@BeforeEach` で前面に出していないと、「クリックしたのに何も起きない」形で
ときどき落ちるテストになる。

前面に出すのは OS 側の仕事であり、`Platform.runLater` が返った時点では終わっていない。
**前面化だけでは足りず、10 回に 1 回ほど取りこぼす。** 「開く」は押した結果が起きたかを
見て、起きていなければ押し直している（`DesktopUiTest#clickUntilAccepted`）。

これは環境の側の揺れであり、吸収してよい類のものである。何を吸収してよく何を
吸収してはならないかは `CLAUDE.md`「不安定なテストの扱い」に書いた。
この事例はそこで挙げている「吸収してよい例」の実体にあたる。

**★ TestFX の `@Start` / `@Stop` は継承されない。**
`ApplicationExtension` は宣言されたメソッドの中からしか探さない。土台クラスに置いても
呼ばれず、フィールドが `null` のまま全部落ちる。`DesktopUiTest` は `setUp` / `tearDown`
を提供し、`@Start` / `@Stop` は各テストクラスが自分で持っている。

**★ 節点は「見つかる」だけでは押せない。**
ダイアログの節点は窓が出る前から存在している。そこへクリックを送ると
「1 nodes, but no nodes were visible」で落ちる。窓が出て、割り付けが済んで、
大きさが入るところまで待つ（`DesktopUiTest#waitForNode`）。

#### 計画と違ったこと ── そして結局、計画のほうが正しかった

**ドラッグ&ドロップは駆動できる。だが CI では使えない。**

着手前は「TestFX は JavaFX の DnD を駆動できない」という前提で、並べ替えは自動化の
対象外にするつもりだった。手元で試すと `drag().dropTo()` で `startDragAndDrop` からの
一連が最後まで通り、書き出した PDF のページ順まで確認できたので、その判断を覆した。

**2026-08-22 の CI 実走で、この 1 本だけが 19 分 20 秒かかった**（他の 24 本は合計 61 秒）。
`build` は 23 分 2 秒で、`timeout-minutes: 30` に対して余裕が 7 分しかない状態になった。
テストは通っている。**落ちるのではなく、遅い。**

原因は TestFX の造りにある。`MoveRobotImpl` はマウスの移動を距離ぶんのステップに刻み
（既定で最大 200）、各ステップを `asyncFx` で JavaFX スレッドへ積む。ドラッグの最中、
そのスレッドは Windows の DnD のモーダルループにいて、積まれた移動を 1 つずつしか捌けない。
ランナーでは 1 つあたり約 5.8 秒（1160 秒 ÷ 200 ステップ）。最後の `move()` がその全部を待つ。

**設定では回避できない**（どちらも実測）。

| 試したこと | 結果 |
|---|---|
| `testfx.robot.move_max_count=1` | **22 本が落ちる。** 刻まないとクリックも DnD も成立しない。JavaFX はマウスの移動を連続したイベントとして見る |
| `testfx.robot=awt`（FX スレッドを経由しない） | **22 本が落ちる。** 手元でも動かない |

距離を詰めればステップ数は減るが（`min(distance, 200)`）、20px まで詰めても 2 分かかる。
しかも 5.8 秒/ステップという値は環境依存で、悪化しても気づけない。

**そこで `ReorderUiTest` は CI から外した**（`@DisabledIfEnvironmentVariable(named = "CI")`）。
手元では 2 秒で通るので消してはいない。**腐ることは承知の上であり、
4-4「人が見るもの」に CI で守られていないことを明記してある。**

**★ この一連で、手元で通ったことを CI で通る根拠に使う誤りを 2 度踏んだ。**
1 度目は「windows ランナーは対話セッションを持つから headed で動く」（結果的に正しかったが、
確かめずに書いた）。2 度目がこの DnD である。**手元と CI は別の環境であり、
片方の結果はもう片方の根拠にならない。**

#### 自動化していないもの

4-4「人が見るもの」を参照。**そこに挙げていないものは自動で見ている、とは読まないこと。**
AI 機能の入口は今この版に無いため、INV-3 について確かめられるのは
「AI 無しで一連の操作が通る」ことと「無いことを画面が正直に伝える」ことの 2 つだけである
（`AiAbsenceUiTest`）。AI を使う画面が入った時点で、その入口が `isAvailable()` で
隠れることをそこに足すこと。

### 整形を Spotless に寄せた（2026-08-22）

整形の判断を機械に移した。**手で整えない。コミット前に `./gradlew spotlessApply` を掛ける。**

#### 改行が混ざっていた

`.gitattributes` が無く、`core.autocrlf` は手元で `false`、global で `input`、system で `true` と
三層で食い違っていた。書いた環境の改行がそのまま index に入り、**LF 82 / CRLF 16 の混在**に
なっていた（`README.md`、`docs/*.md`、`pdf-desktop` の Java 8 本、`pdfjig.css` などが CRLF）。

`* text=auto eol=lf` を正とし、Windows のシェルが読む `*.bat` / `*.cmd` / `*.ps1` だけを
チェックアウト時に CRLF へ戻す。`gradlew` は ubuntu ランナーが `sh` で実行するため明示的に固定した。

★ **Spotless を素で入れてはならなかった。** `lineEndings` の既定は `.gitattributes` が無いと
git の設定へフォールバックし、Windows では CRLF 側に倒れる。LF の 82 ファイルを書き換えに行き、
ubuntu と windows で判定が食い違って CI が割れる。**取り決めを先に置き、Spotless には参照させる。**

★ Gradle では `LineEnding.GIT_ATTRIBUTES` を指定できない（例外になる。
[spotless#1274](https://github.com/diffplug/spotless/issues/1274)）。使えるのは
`GIT_ATTRIBUTES_FAST_ALLSAME` だけであり、これは **対象が全部同じ改行** という前提で判定を省く。
その前提は「CRLF で残す `*.bat` / `*.ps1` を Spotless の対象に入れていない」ことで成り立っている。
**それらを target に足すと、混在を最初の 1 ファイルで代表して黙って改行を壊す。**

#### 何を選んだか

| 対象 | 何を使うか | なぜ |
|---|---|---|
| Java | palantir-java-format（4 スペース / 120 桁） | 既存が 4 スペース。100 桁だと 530 行が折り返される |
| `*.gradle.kts` | ktlint（`ktlint_official`） | 既定のまま。スタイルの好みで例外を作らない |
| md / yml / toml / css | 行末の空白と末尾の改行だけ | 整形はしない。`.md` の意図的な行末 2 スペースは 0 件と確認済み |

- **palantir は Javadoc を整形しない。** 懸念していた日本語の桁揃え（`@param path     入力ファイル`）は
  無傷で残った。google-java-format はこれを潰すので、**乗り換えるならその点を見ること**
- **`formatAnnotations()` は入れていない。** `@SuppressWarnings` の位置を動かす副作用が
  `-Werror -Xlint:all` と噛み合ったときに読みにくい
- ktlint は代入の右辺を改行して字下げする（`val x =` の次の行から `listOf(`）。
  Gradle DSL では見慣れないが、機械に任せた以上は例外を作らないことを選んだ
- 逃げ道として `toggleOffOn()` を有効にしてある（`// spotless:off` 〜 `// spotless:on`）。多用しないこと

適用の実差分は 549 行追加 / 578 行削除、41 ファイル。Java 8,513 行に対してこの程度で済んだのは、
既存が google-java-format 系の作法（static import 先頭、ASCII 順、ワイルドカード禁止）で
書かれていたためである。行末の空白と末尾改行の欠落は導入前から 0 件だった。

#### CI とワークフロー

`spotlessCheck` は `check` に自動で載るため、**既存の `./gradlew build` がそのまま検査になる**。
ワークフローもジョブも増やしていない（`CLAUDE.md` の CI 節）。

#### 版を追わせる仕掛け

palantir と ktlint の座標を `libs.versions.toml` の `[libraries]` に宣言してあるが、
**これはどのモジュールの依存にも入らない。** Spotless は自分の classloader で解決するため、
書いた座標は解決に使われない。`[versions]` だけでは Dependabot が座標を知らず版が固まるので、
**追わせるためだけの宣言である。消すと更新が来なくなる。**

版上げは `formatting` グループに寄せてあり、3 つまとめて 1 本の PR で来る
（`.github/dependabot.yml`）。連動して整形結果を変えるものを別々に受けると、
`spotlessApply` を 3 回掛けることになるためである。

**2026-08-22 の update job で実際に確かめた。** グループ化した直後に Dependabot が設定を
読み直して走り、次のことが分かった。

- **Dependabot は `[plugins]` を見ている。** `com.diffplug.spotless` は素の id のまま
  Dependency Snapshot に現れ、`formatting` グループに入った。マーカー座標
  （`…:com.diffplug.spotless.gradle.plugin`）にはならない
- **`[libraries]` に宣言しただけの palantir / ktlint も追われている。**
  「Dependabot に版を追わせるためだけの宣言」は狙いどおりに効いている
- ★ **`javafx = "21.0.7"` は追われていない。** Dependency Snapshot に出るのは
  `org.openjfx.javafxplugin`（プラグイン側、`version.ref` は `openjfx-plugin`）であり、
  `[versions]` の `javafx` はどの `[libraries]` からも `version.ref` されていないため
  視界に入らない。**JDK 21 に留める方針の間は実害がないが、誰も追っていないことは事実である。**
  追わせるなら `org.openjfx.jmods:jmods` を `[libraries]` に宣言する

#### 整形ツールの版が上がったとき

`formatting` グループの PR は **CI が落ちることがある。壊れているのではない。**
版が上がって整形規則が変わり、既存コードが新しい規則を満たさなくなっただけである。

1. PR のブランチを取り込む
2. `./gradlew spotlessApply`
3. 差分が出たら `style:` のコミットを足す
4. 差分が広範なら `.git-blame-ignore-revs` にそのコミットを足す
5. `./gradlew build` が通ることを確かめて受ける

★ **major の版上げは差分を見てから決めること。** ktlint 2.0 は `ktlint_official` の
ルールが変わり、受けると全 `*.gradle.kts` が書き換わりうる。

★ **自動で `spotlessApply` を掛けて push するワークフローは作っていない。**
`contents: write` を持つジョブを増やすことになり、得られるのは 1 コマンド打つ手間の
削減でしかない。**割に合わないと判断した。**

#### blame

改行の正規化と一括整形は `.git-blame-ignore-revs` に載せた。GitHub は自動で参照する。
手元では `git config blame.ignoreRevsFile .git-blame-ignore-revs` が要る。
**載せてよいのは中身を変えていないコミットだけである。**
整形と実装が混ざったコミットを載せると、blame から本物の変更まで消える。
